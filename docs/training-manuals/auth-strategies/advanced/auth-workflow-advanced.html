1. Auth in Workflows vs. Tests

In standalone tests, auth is configured directly on the Scenario (or inherited from Feature Group → Global Profile). In workflows, auth resolution is more complex because each HTTP node can target a different service with different credentials.

2. Service Registry Auth

When an HTTP node is bound to a Service Registry entry (serviceId), auth is resolved from the service's endpoint matrix.

resolveServiceAuth()

export function resolveServiceAuth(
  data: HttpNodeData,
  services?: WorkflowService[],
  selectedEnvId?: string,
  microservices?: Microservice[],
  globalAuthProfiles?: GlobalAuthProfile[],
) {
  // 1. Find the service
  const svc = services.find(s => s.id === data.serviceId);

  // 2. Check endpoint matrix for selected env
  const ep = svc.endpoints.find(e =>
    e.envId === selectedEnvId && e.enabled
  ) ?? svc.endpoints.find(e =>
    e.envId === '__all__' && e.enabled
  );

  // 3. Custom auth on endpoint row
  if (ep?.authMode === 'custom' && ep.auth) return ep.auth;

  // 4. Inherit from microservice authProfileIds
  const envAuth = resolveEnvAuth(svc, selectedEnvId,
    microservices, globalAuthProfiles);
  if (envAuth) return envAuth;

  // 5. Service defaultAuth
  if (svc.defaultAuth) return svc.defaultAuth;

  // 6. Legacy per-env auth
  if (svc.authPerEnv?.[selectedEnvId]) return svc.authPerEnv[selectedEnvId];

  // 7. Legacy service auth
  return svc.auth;
}

Endpoint Auth Modes

authModeBehaviorUse Case
inherit Uses service defaultAuth, or linked microservice's auth profile Most endpoints — same auth across envs
custom Uses endpoint-specific auth config Different tokens per environment
💡 Per-Environment Tokens Use authMode: 'custom' on each endpoint row to configure different API keys or tokens per environment. The test environment might use a sandbox key while production uses a live key.

3. ServiceEndpoint Type

export interface ServiceEndpoint {
  envId: string;              // environment ID, or '__adhoc__'
  url: string;                // base URL for this env
  enabled: boolean;           // service available in this env?
  authMode: 'inherit' | 'custom';
  auth?: AuthConfig;          // only when authMode === 'custom'
  source: 'manual' | 'microservice'; // how URL was populated
}

WorkflowService Auth Fields

export interface WorkflowService {
  id: string;
  name: string;
  endpoints: ServiceEndpoint[];

  /** Fallback auth for endpoints with authMode='inherit'. */
  defaultAuth?: AuthConfig;

  /** Linked microservice — auto-populates URLs and auth. */
  microserviceId?: string;

  // Legacy fields (migration compat):
  auth?: AuthConfig;
  authPerEnv?: Record<string, AuthConfig>;
}

4. Microservice Auth Profile Resolution

When a service is linked to a microservice and the endpoint uses authMode: 'inherit', auth is resolved from the microservice's per-environment auth profile:

function resolveEnvAuth(
  svc: WorkflowService,
  envId: string,
  microservices: Microservice[],
  globalAuthProfiles: GlobalAuthProfile[],
): AuthConfig | undefined {
  // Find the linked microservice
  const ms = microservices.find(m => m.id === svc.microserviceId);

  // Look up the auth profile ID for this environment
  const profileId = ms?.authProfileIds?.[envId];

  // Find the global auth profile
  const profile = globalAuthProfiles.find(g => g.id === profileId);

  return profile?.auth;
}
Microservice Auth Chain

WorkflowService (microserviceId: "ms-1")
→ Microservice (authProfileIds: { "test": "gap-1", "prod": "gap-2" })
→ GlobalAuthProfile (id: "gap-1", auth: { type: "bearer", token: "test-token" })
→ AuthConfig applied to HTTP node

5. Workflow Auth Profiles

Workflow Auth Profiles are an older mechanism for sharing auth across HTTP nodes. Each workflow stores an array of WorkflowAuthProfile objects:

export interface WorkflowAuthProfile {
  id: string;
  name: string;
  auth: AuthConfig;   // bearer, basic, apiKey, oauth2, etc.
}

How Nodes Reference Auth Profiles

HTTP nodes can reference a profile via authProfileId:

// In resolveHttpAuthForGraph():
const resolveHttpAuthForGraph = (data: HttpNodeData) => {
  // 1. Try Service Registry auth first
  const svcAuth = resolveServiceAuth(data, workflowServices,
    selectedEnvId, microservices, globalAuthProfiles);
  if (svcAuth) return svcAuth;

  // 2. Fall back to Workflow Auth Profile
  if (!data.authProfileId) return undefined;
  return workflowAuthProfiles.find(p => p.id === data.authProfileId)?.auth;
};
⚠️ Service Auth Takes Priority If an HTTP node has both a serviceId and an authProfileId, the Service Registry auth always wins. The Auth Profile is only used as a fallback when no service auth is found.

6. The useWorkflowResolvers Hook

The useWorkflowResolvers hook centralizes both URL and auth resolution for the workflow engine:

export function useWorkflowResolvers({
  selected, previewWorkflow, selectedEnvId, resolvedBaseUrl,
  environments, microservices, globalAuthProfiles,
  workflowHostProfiles, workflowAuthProfiles, workflowServices,
  selectedNode, onEnvSelect, update,
}) {
  // Per-workflow environment persistence
  const handleEnvSelect = useCallback((envId) => {
    onEnvSelect(envId);
    if (selected && !previewWorkflow)
      update(selected.id, { lastSelectedEnvId: envId });
  }, [/* deps */]);

  // Base URL resolution for graph runner
  const resolveHttpBaseUrlForGraph = useCallback(
    (data) => resolveHttpNodeBaseUrl(data, microservices,
      workflowHostProfiles, workflowServices, selectedEnvId),
    [/* deps */],
  );

  // Auth resolution for graph runner
  const resolveHttpAuthForGraph = useCallback(
    (data) => { /* service auth → auth profile fallback */ },
    [/* deps */],
  );

  return {
    handleEnvSelect,
    resolveHttpBaseUrlForGraph,
    resolveHttpAuthForGraph,
    effectiveQuickTestBaseUrl,
  };
}

Both resolveHttpBaseUrlForGraph and resolveHttpAuthForGraph are passed to useWorkflowExecution, which feeds them into the graph runner's handler context.

7. Per-Node Auth Override

Every HTTP node also has inline auth on its scenario. This is the lowest priority — it's used only when no service auth and no auth profile is configured:

// HttpNodeData → scenario → auth
export interface HttpNodeData {
  label: string;
  scenario: Scenario;       // contains .auth: AuthConfig
  serviceId?: string;        // Service Registry binding
  authProfileId?: string;    // Workflow Auth Profile
  // ...
}

// Resolution order in the graph runner:
// 1. resolveHttpAuthForGraph(data)   — service + profile
// 2. data.scenario.auth              — inline fallback

9. Environment Switching

When you switch environments in the workflow harness bar, both URLs and auth are re-resolved:

  • URLs: resolveServiceBaseUrl() looks up the endpoint row for the new env.
  • Auth: resolveServiceAuth() looks up the endpoint auth or microservice profile for the new env.
  • Persistence: The selected env is saved per-workflow via lastSelectedEnvId.
// Per-workflow env persistence:
const handleEnvSelect = (envId: string) => {
  onEnvSelect(envId);  // updates harness bar
  if (selected && !previewWorkflow) {
    update(selected.id, { lastSelectedEnvId: envId });
  }
};

// On workflow switch — restore saved env:
useEffect(() => {
  if (selected?.lastSelectedEnvId) {
    onEnvSelect(selected.lastSelectedEnvId);
  }
}, [selected?.id]);
📘 Quick Test URL vs. Service URL The effectiveQuickTestBaseUrl prioritizes the selected node's service URL over the harness bar URL. This means if you select a node bound to a service, the Quick Test button targets that service's URL — not the default harness URL.

10. Exercises

Exercise 1: Service Registry Auth

Goal: Configure a workflow service with per-environment auth.

  1. Open the Service Registry panel in a workflow.
  2. Create a service "Payment API" with two endpoint rows:
    • test: URL = https://api.test.stripe.com, authMode = custom, auth = Bearer sk_test_...
    • prod: URL = https://api.stripe.com, authMode = custom, auth = Bearer sk_live_...
  3. Add an HTTP node and bind it to "Payment API" (serviceId).
  4. Switch environments — observe the URL and auth change together.
  5. Run Quick Test in each environment — verify the correct token is sent.

Exercise 2: Workflow Auth Profile Fallback

Goal: Set up an Auth Profile and see how it falls back.

  1. Create a Workflow Auth Profile: name "Internal API", type Bearer, token "internal-tok".
  2. Add an HTTP node with authProfileId pointing to this profile (no serviceId).
  3. Run Quick Test — verify the Bearer token is applied from the profile.
  4. Now bind the node to a Service with defaultAuth set to a different bearer token.
  5. Run again — the Service auth wins over the Auth Profile.

Exercise 3: Microservice Auth Chain

Goal: Trace the full microservice → global auth profile chain.

  1. Create a Global Auth Profile: name "Warehouse Bearer", token "wh-tok".
  2. Create a Microservice: name "Warehouse", set authProfileIds.test to the profile ID.
  3. Create a Workflow Service linked to this microservice (microserviceId).
  4. Add an endpoint row: envId test, authMode inherit.
  5. Bind an HTTP node to this service.
  6. Run Quick Test — verify the "Warehouse Bearer" token is applied via the chain.
